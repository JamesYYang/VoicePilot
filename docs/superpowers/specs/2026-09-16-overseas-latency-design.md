# 海外同事延迟与部署位置设计（含替代模型调研）

> **要解决的现象**：第一个试用者人在美国（挂公司 VPN），模型端点在 `cn-beijing`（ping ≈ 200ms），反馈**「恒定慢一截，但能用」**。
> **上游**：`docs/release-checklist.md`（2026-09-16 首次试用包已发出）、`docs/plans/2026-09-05-voicepilot-prd.md` §4.1 / §5.2 / §6、`server/config-endpoint/README.md`。
> **本文件的性质**：一轮**调研 + 决策 + 拆线**。第 6 节设计到可实现；第 7/8 节只到「边界与前置项」，**不在本轮启动**。

## 0. 一句话结论

**当前的主因不是模型在北京，而是我们每次听写都要重新建一条 WebSocket —— 4–6 个 RTT 被 200ms 的 RTT 放大成约 1 秒，每按一次快捷键付一次。**

所以正确的第一步是**连接预热**（第 6 节）：与地域、模型、部署位置全部无关，改动最小，国内同事也受益。「换区域 / 换模型 / 私有化部署」都不是当前症状的解，理由见第 5 节。

## 1. 问题与成功判据

### 1.1 现象（已定性）

用户描述：**恒定慢一截，但能用** —— 不是卡顿、不是断流、不是越说越落后。

这一条定性的价值在于它**排除了两类病因**：

| 病因 | 特征 | 是否吻合 |
|---|---|---|
| 跨太平洋**丢包/抖动/拥塞** | 偶发卡住几秒、灰字一阵一阵、断线重连 | ❌ 不吻合 |
| **RTT × RTT 次数**（往返次数多） | 稳定的、可预期的慢，不随网络状况波动 | ✅ 吻合 |

> ⚠️ 这条定性来自用户转述，**尚未用仪器确认**。第 6.6 节给了零改动的取证方法。

### 1.2 成功判据（**待确认 —— 本文件唯一的阻塞性开放问题**）

| 候选判据 | 说明 |
|---|---|
| **P1（推荐）** | 美国同事的「出声→首字」落进 §6 预算（< 800ms）或国内基线 +200ms 以内 |
| P2 | 体感「和国内同事差不多」 |
| P3 | 只要求「比现在明显好」 |

选 P1 的理由：它是**可测的**，而且 §6 已经有阈值。选 P2/P3 会让「要不要动地域」这类大决策失去判据。

## 3. 已核实的现状（本仓库）

### 3.1 端点硬编码在两处，凭据与下发都只有两个字段

| 位置 | 内容 |
|---|---|
| `app/electron/asr/session.js:121` | `wss://${this.#workspaceId}.cn-beijing.maas.aliyuncs.com/api-ws/v1/inference` |
| `app/electron/llm/polish.js:21` | `https://${workspaceId}.cn-beijing.maas.aliyuncs.com/compatible-mode/v1/chat/completions` |
| `app/electron/asr/config.js` | 凭据 = `{apiKey, workspaceId}`（Key 加密、workspaceId 明文） |
| `server/config-endpoint/server.js:38` | 下发 = `{version, apiKey, workspaceId}` |

→ **今天做不到「按人/按办公室切节点」**，但只差一个字段 —— 下发的 payload 本来是「按人发配置」的机制。

### 3.2 每次听写都新建 WebSocket（**本设计的正身**）

`AsrSession.start()`（`app/electron/asr/session.js:115`）里 `new WebSocket(...)`，**无复用、无预热**，且必须串行走完：

```
DNS → TCP(1 RTT) → TLS(1–2 RTT) → WS upgrade(1 RTT) → run-task → task-started(1 RTT)
```

### 3.3 ⚠️「不预热会话」是**刻意决策**，不能直接推翻

`app/electron/session/machine.js:24-25` 原文：

> **不预热会话**。百炼按 usage.duration 计费，静音也计费，常驻空会话白烧钱。会话在按下快捷键时才建立（PRD §4.1）。

**这条约束决定了设计边界**：预热只能预建「**连接**」（TCP+TLS+WS，不发 `run-task`），**不能常驻「任务」**。见 6.2。

### 3.4 埋点依赖字级时间戳；产品分段依赖 `sentence_end`

- `app/electron/telemetry/metrics.js` 算 首字 / 跟随 / 定稿 **全靠** `words[].begin_time` / `end_time`。
- **产品功能不依赖** `words` —— 「每句一行」的分段靠 `sentence_end`（`app/electron/asr/session.js:173`）。
- 另：`session.js:165` 用 `s.words?.length` 做空事件过滤，换成只看 `s.text` 即可。

### 3.5 「音频不丢」靠 warming 缓冲，与本设计正交

PRD §4.1 第 2 条：建会话期间照常采集并本地缓冲，`task-started` 后立刻 flush。队列上限 30 帧（≈3 秒，`app/electron/session/audio-queue.js:23`）。

→ **美国同事现在的音频并没有丢**（~1 秒 < 3 秒上限），丢的是**时间**。本设计不碰这条路径。

## 4. 延迟构成与量化

| 环节 | 国内（RTT ≈ 30ms） | 美国同事（RTT ≈ 200ms） |
|---|---|---|
| 建连 4–6 个 RTT | ~150ms | **~800–1200ms**（每次听写） |
| 稳态：每个事件 1 个 RTT | 跟随 P50 = 208ms（**已含国内 RTT**） | 跟随 P50 → **~380ms**（+1 个 RTT 的差值 ≈ +170ms） |
| 句尾定稿 | ~1014ms | **~1.2s** |
| 「出声→首字」体感合计 | ~620ms | **~1.3–1.7s**（= 国内基线 + 建连多出的 ~700ms + 稳态 ~170ms） |

> 数字来源：`docs/plans/2026-09-05-voicepilot-prd.md` §6 列 首字 618 / 跟随 P50 186 / 定稿 950，§8 的 M2 离线回放实测是 首字 617 / 跟随 P50 208 / 定稿 P50 1014。本文件统一用**实测那一组**（§8），与 `VP_*_SELFTEST` 口径一致；两者差在采样与批次，不改变量级。

**结论**：建连一项就占了美国同事多出来的延迟的**大部分**，而它**与模型、地域、部署位置全部无关**。

## 5. 方案与取舍

| # | 方案 | 收益 | 代价 | 判定 |
|---|---|---|---|---|
| **A** | **连接预热/复用** | 每次听写省 **~600–800ms**（美国）、~100ms（国内） | 改连接生命周期；需先 spike 验服务端行为 | ✅ **本轮唯一推荐启动** |
| B | 只把润色搬到 `us-east-1` | ~200ms TTFT | 需按人下发 region + 新地域业务空间/Key；ASR 搬不动 | ⏸ 触发条件：A 做完仍不达判据，且润色是体感瓶颈 |
| C | 接受，写进试用说明 | 0 | 无 | ⏸ 兜底 |
| D | 多节点（境内 + 美国各一套，换开源模型） | **唯一能真正把 RTT 降下来** | 换模型的完整账单 + GPU + 海外运维 + 合规 | ⏸ 触发条件：判据是 P1 且公司愿意在海外放节点 |
| ~~E~~ | ~~自建中转（香港/新加坡反代）~~ | — | **对「恒定慢」是负收益**：RTT 不会变小，只多一跳 | ❌ 主动排除（若将来测出丢包/抖动再重开） |

### 5.1 一条要反复纠正的直觉

**公司 VPN / 专线不能让 RTT 变小。** 美↔中 RTT 的物理下限就是 ~150–200ms（光速 + 海底光缆路由）。专线能治的是**丢包、抖动、高峰期拥塞**，改不了中位数。

所以「部署到公司内部 → 各办公室都快」这个推理，**在单点（境内）部署时不成立**；成立的是**多节点**：美国侧也放一套，就地接入。公司的全球办公室与内部 VPN 是**多节点部署的落点资产**，不是「让 RTT 变小」的手段。

## 6. 线一：连接预热（设计到可实现）

### 6.1 目标与非目标

**目标**：把每次听写的**建连 RTT 从 4–6 个降到 1 个**（只剩 `run-task → task-started`）。

**非目标**（明确不做）：
- ❌ 不常驻「任务」（违反 3.3 的计费决策）。
- ❌ 不改稳态行为（送帧、flush、背压、A7 全部不动）。
- ❌ 不改 `sentence_end` / 分段 / 埋点口径。
- ❌ 不改地域、不换模型。

### 6.2 关键约束：预热只能预建「连接」

`run-task` 发起后才计 `usage.duration`（含静音）。所以：

```
可预建：DNS + TCP + TLS + WS upgrade   ← 空闲、不 run-task、不计费
不可预建：run-task / 音频 / finish-task  ← 按下快捷键才发生
```

**（待 spike 确认）**：服务端是否允许「已连接但未 run-task」的 WS 长期存在；空闲超时是多少；是否允许**同一连接上连续多次** `run-task → finish-task`。

### 6.3 架构：把 `AsrSession` 拆成「连接」与「任务」

现在 `AsrSession` 同时持有连接与任务（`start()` = 建连 + run-task + 等 task-started）。拆成两层：

| 单元 | 职责 | 生命周期 |
|---|---|---|
| **`AsrConnection`** | DNS/TCP/TLS/WS 握手；心跳/保活；断线检测与重连；对外暴露「就绪 / 已死」 | **进程级单例**，跨听写复用 |
| **`AsrTask`** | 在一次就绪连接上发 `run-task` → 等 `task-started` → 承接 `result-generated` → `finish-task` | **每次听写一个**，task_id 依旧是新的 |

**对外契约不变**：`AsrTask` 对 `SessionMachine` 暴露的接口与现在的 `AsrSession` 一致（`start()` / `sendAudio()` / `stop()` / `abort()` / `state` / `bufferedBytes` / `isOpen` / `onResult` 等）。这样：

- `SessionMachine` 的 `#createSession` 注入点**保留**（自测三条异常收敛路径不受影响）；
- `#pump()` 的 `session.state === 'streaming'` 闸门不变；
- `resetSegment()`（新 task_id → 重置埋点原点）**逻辑不变**，因为每次听写仍然是新 task。

**回调归属要划清**（否则会出「连接死了但没人知道」的静默故障）：

| 回调 | 归属 | 理由 |
|---|---|---|
| `onResult` / `onLifecycle`（task-started / task-finished） | **`AsrTask`** | 都是 task 级事件，且埋点原点与 task_id 绑定 |
| `onError` / `onClosed` | **`AsrTask`**（由 `AsrConnection` 转交） | `SessionMachine` 的 `#onSessionError` / `#onSessionClosed` 已经按「会话期 vs 空闲期」分好了（见 6.5），把连接级故障转交给当前 task 即可，**不新增状态机路径** |

**`AsrConnection` 只暴露两件事**给上层：`ready`（是否已建好、可直接 `run-task`）与「死了」的通知。它**不认识**状态机、不碰窗口、不碰焦点。

### 6.4 预热时机与生命周期

| 时机 | 动作 |
|---|---|
| 应用启动、拿到凭据后 | 异步建一条连接（失败静默，不打扰用户） |
| 每次会话回到 `idle` | 确保有一条就绪连接（异步补齐） |
| 按下快捷键、连接已就绪 | **只发 `run-task`** —— 省掉 3–4 个 RTT |
| 按下快捷键、连接未就绪 | 退回现有行为（边建边缓冲音频），**绝不阻塞** |

> ⚠️ **预热绝不能延后会话开始**。`warming` 必须立刻开始采集与渲染，预热只是「运气好时省一截」。

### 6.5 失败处置

| 情形 | 处置 |
|---|---|
| 预热失败（无网 / 证书 / 401） | 静默记日志，**不弹任何提示**；下次按快捷键走现有路径（该报错时才报错） |
| 连接在空闲期被服务端关闭 | 视为「未就绪」→ 空闲期按退避重连；不产生用户可见状态 |
| 按下快捷键时连接刚死 | `run-task` 失败/超时 → 走**现有**的 `#scheduleRetry` 退避与 `#failToReviewing` 收敛，**不新增路径** |
| 限流/断线后重试 | **先看连接是否还活着**：活着就直接复用（只重发 `run-task`），死了才重建。否则重试会退化成「每次重试都重连」，把本设计在异常路径上白扔掉 |
| 写回/`reviewing` 期间连接变化 | 与本设计无关（连接不参与窗口与焦点） |
| 凭据变更（重新取 Key / 改 region） | **作废并重建连接**（旧 Key 的连接不可复用） |

### 6.6 前置 spike（**先做这个，再动实现**）

| # | 要回答的问题 | 怎么验 |
|---|---|---|
| S1 | 服务端是否允许「连上但不 `run-task`」并保持多久？ | 脚本建连后静默，按 10s/30s/60s/300s 分档，观察是否被关闭 |
| S2 | 是否允许同一连接上连续多次 `run-task → finish-task`？ | 同一连接上跑两轮完整任务，看第二轮是否成功 |

| S4 | 空闲期的**保活**方式（是否要发 ping / 服务端是否发 ping）？ | 抓包或看 `ws` 的 ping/pong 日志 |

> S3 是**否决性**的：若空闲连接也计费，本设计直接放弃（回到「不预热」的现有决策）。

### 6.7 怎么验（本线）

1. **门禁**：`tsc` 干净 + 现有四套 `VP_*_SELFTEST`（SM / INJECT / UI / BAR）全绿，**断言值不动**。
2. **新增断言**：`AsrTask` 在「连接已就绪 / 连接未就绪 / 连接中途死掉」三种输入下的行为（用注入的假连接，与现有 `createSession` 注入同一个手法）。
3. **真机量化**：给埋点补一个 `connectMs`（`markToggle` → 第一个 `onSend` 的 `sentAtMs`）—— **数据已经在代码路径里，只是没输出**（`machine.js:286` 的 `markToggle`、`metrics.js:76` 的 `onSend`）。跑同一段话对比预热前后。
4. **国内基线不许退化**：跟随 P50 仍应 ≈ 208ms。

## 7. 线二：多节点下发的配置能力（设计，未启动）

**只有当第 5 节的 B 或 D 被触发时才做。**

### 7.1 两个 host 必须能分别配

**关键点**：ASR 只有北京/新加坡，润色可以到 `us-east-1` —— **两者可能落在不同地域**。所以不能只加一个 `region`。设计：

```
下发 payload 从  { version, apiKey, workspaceId }
扩为            { version, apiKey, workspaceId, asrRegion?, llmRegion?, asrHost?, llmHost? }
```

- 优先级：显式 `*Host`（完整主机名）> `*Region`（拼 `{workspaceId}.{region}.maas.aliyuncs.com`）> 默认 `cn-beijing`。
- **向后兼容**：旧 payload / 旧 `credentials.json` 没有这些字段 → 用默认值，行为与今天完全一致。
- 凭据文件同步扩字段（`workspaceId` 是明文存的，region 同级处理）。

### 7.2 为什么不直接暴露给试用者

**不做 UI**。节点由服务端按人下发 —— 试用者不需要知道也不需要选。这也符合 M5-A 的「Key 不随包外泄、不人手一份」的既定边界。

### 7.3 风险

- **每个地域一套业务空间 + 一套 Key** → 运维与轮换成本线性上升；这是 B/D 的真实代价之一。
- **模型可用性各地域不同** → 下发前必须校验该 region 真有这两个模型，否则会出现「装完拿不到结果」。

## 8. 线三：替代模型与协议适配层（设计 + 未决，未启动）

### 8.1 触发条件

**只有判据是 P1（1.2 节）且公司愿意在美国侧放节点时才启动。** 否则先做 A。

### 8.2 内部事件契约保持不变

`SessionMachine` 只认这一个形状（`app/electron/asr/session.js:170`）：

```js
onResult({ recvAtMs, text, sentenceEnd, sentenceId, beginTime, endTime, words })
```

→ **协议适配层就是「把任意后端的事件映射到这个形状」**。实现上按后端分文件：

| 适配器 | 后端 |
|---|---|
| `dashscope-realtime` （现有） | 北京 / 新加坡 |
| `openai-realtime` | Qwen3-ASR（vLLM）等 OpenAI 兼容后端 |

**硬要求**：适配器**必须产出等价的「句尾」信号**（现在由 DashScope 的 `sentence_end` 提供）—— 否则「每句一行」的分段判据（09-12 定稿）无处安放。OpenAI realtime 侧要看的对应物是 `speech_stopped` / transcription completed 类事件，**（待验）**。

### 8.3 上下文增强怎么办（**本项目最大的单点风险**）

百炼的 **prompt 上下文增强**是目前唯一被实测证明有效的准确率手段（03-mixed 字准确率 91.6% → **98.95%**，术语命中 5/9 → **9/9**）。**开源侧没有文档化的等价物。**

- Fun-ASR-Nano：只有热词（RAG），而热词在我们的实测里是**负收益**（CER 0.1329 → 0.2081，并诱发幻觉）。
- Qwen3-ASR：是 **LALM + chat 接口**，**理论上可以把专名表/格式指令放进 prompt** —— 但这是**推断，必须自验**。

→ **这一条决定「能力是否接近」，是 8.5 评测的唯一判据。**

### 8.4 埋点口径要改（且旧数字不能横比）

替代模型的**流式不返回字级时间戳**（Qwen3-ASR 明确如此）。`metrics.js` 现在靠 `words[].end_time` 定位「这段音频是何时送出的」。

**改法**：改用「**已送出的最大音频位置**」近似 —— `sentAtOf(最后一条 sendLog 的 audioMs)`。

**必须写进文档的是**：这会把「服务端解码窗口」也算进来，**口径变了**，所以：
- 旧基线（首字 618ms / 跟随 186–208ms / 定稿 950–1014ms）**不能与新模型的数字直接比**；
- 换模型必须**重建 PRD §6 的基线**，并同步改 §6 的「现有基线」列。

### 8.5 前置评测清单（同素材、同口径）

复用现成的 `spike/` 工具链，三段素材各跑一遍，与百炼的数字对齐：

| # | 素材 | 判据 |
|---|---|---|
| 1 | **03-mixed** | 英文缩写**命中数**与**大小写**——「上下文增强能否被替代」的唯一判据 |
| 2 | **05-pauses** | 末尾幻觉是否复现（百炼 s400 下 3/3 出现） |
| 3 | **04-terms** | 热词是正收益还是负收益（百炼上是负收益） |
| 4 | 跟随节奏 | 把刷新间隔往 100ms 级压，看 GPU 代价与延迟曲线 —— **对标百炼的 100ms 粒度**（Fun-ASR 社区用 0.48s、官方建议 0.8s，粗 5–8 倍） |
| 5 | 0.6B vs 1.7B | 准确率差值是否值多出的显存 |

> ⚠️ 不要拿技术报告自报的 WER/CER 直接比 —— 测试集不同、WER ≠ CER。

### 8.6 运维代价（别低估）

- **流式依赖 vLLM nightly**（`--pre`）→ 版本是移动靶（与 FunASR「v1.4.3 的 `final after STOP` 是 19.5 秒、加批处理才 414ms」是同一类坑：**选版本 = 选可用性**）。
- GPU 与并发要自己扛；**不能拿云端 20 路并发上限当本地容量**。
- **润色 LLM 必须一起私有化**，否则「语音在内网、润色出公网」等于白做。
- 部署位置：**必须在美国侧**，否则 RTT 一分不少（5.1 节）。

## 9. 明确不做

- ❌ **自建中转**（香港/新加坡反向代理）—— 对「恒定慢」是负收益。
- ❌ 把节点放在**境内**再期望美国同事变快 —— 不解决 RTT。
- ❌ 为「按人切节点」做 UI —— 节点由服务端下发，试用者无感。
- ❌ 为了延迟而顺手改分段/埋点口径 —— 口径变更只在换模型的场景下发生（8.4）。
- ❌ 换模型时不重建 §6 基线 —— 那会让所有延迟结论失去可比性。

## 11. 顺序
