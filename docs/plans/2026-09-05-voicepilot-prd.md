## 1. 产品定位

一个常驻桌面的语音输入工具。按全局快捷键开始说话，文字**实时**出现在桌面右下角的半透明悬浮条上；说完后可以直接复制，也可以展开成完整应用做润色、调整场景与语气。

### 1.1 明确的边界（不是什么）

| 不是 | 说明 |
|---|---|
| **不是输入法** | 不接管键盘、不替换系统输入法、**不在光标处直接插入文字**。v1 的终点是剪贴板。 |
| **不是会议转写工具** | v1 只处理一个人的麦克风输入。会议记录是后续方向，本期不投入。 |
| **不是云服务** | 音频只在识别过程中上传，不留存；文本只存本地。 |

**「不是输入法」这条是被刻意选择的**，不是能力不足：直接注入光标要处理剪贴板竞态、中文 IME 组字态（Ctrl+V 会被吞）、管理员权限窗口、终端回退四个坑，且 Windows 与 macOS 各写一遍。v1 先绕开，把全部精力压在「丝滑」上。

### 1.2 两个形态

| | 悬浮条（Mini） | 主应用（Studio） |
|---|---|---|
| 触发 | 全局快捷键 | 悬浮条点「润色」 |
| 位置 | 桌面右下角，半透明，置顶 | 普通应用窗口 |
| 焦点 | **永不抢焦点** | 正常获取焦点 |
| 职责 | 实时听写 + 复制 + 润色入口 | 润色、场景/语气、历史回看与搜索 |
| 关闭 | 复制后淡出（可设为保留）/ Esc | 手动关闭 |

**「不抢焦点」是硬性技术定义，不是视觉描述**：从悬浮条出现到消失，目标应用的光标位置、选区、输入焦点、输入法状态**不得发生任何变化**。Windows 与 macOS 的实现方式完全不同（§5.6），是 v1 里平台差异最大的一块。

### 1.3 首发范围：公司内部试用

v1 不对外发布，**先给公司内部 50 人以上使用**。这是刻意选择：识别质量、延迟体感、快捷键冲突、权限引导这些问题，只有在真实用户的真实机器上才会暴露，闭门开发猜不出来。

由此确定的取舍：

| 因此不需要 | 因此需要加强 |
|---|---|
| 商店上架与审核 | 内部分发渠道 + 自动更新（§5.9） |
| 定价、付费墙、账号体系 | 遥测、错误标记、诊断导出（§5.10、F13） |
| 用户自带 API Key | 集中配置下发（F11） |
| 营销 material | 非技术同事的权限引导（§5.7） |

## 2. 目标用户与场景

### 2.1 第一批用户：公司内部同事

已确认的日常口述内容是两类：

- **邮件与即时消息**——术语密度低，通用识别足够，主要是语气和格式需求
- **文档、需求与周报**——长文本口述，术语是**产品名称、内部系统名、项目代号、同事姓名**

**关键判断：内部同事 ≠ 跨境电商卖家。** 公司虽然服务跨境卖家（SellingPilot），但内部同事写的是需求和周报，嘴里说的是产品名和项目代号，不是 FBA / ACOS / listing。因此**已实测的跨境电商词表不适合这批用户**，本期不启用（§5.3）。

### 2.2 后续用户

内部试用跑顺之后再对外。**垂直行业（含跨境电商）的选择等那时候的真实数据决定**，不由我们现在拍。

## 4. 交互流程

### 4.0 首次使用引导（F8）

安装后首次启动，只问**一个问题**：你的工作主要涉及哪个领域？

| 选项 | 效果 |
|---|---|
| **通用**（默认，可直接跳过） | 不加载词表 |
| 产品与研发 | 加载公司内部专名表 |
| 其他 | 不加载词表，后续可在设置中自定义 |

选择**同时驱动两层**（一次选择两处生效，用户不用配两遍）：

| | ASR 层 | LLM 润色层 |
|---|---|---|
| 作用 | 加载领域词表 → **听对词** | 场景预设的默认值 → **写得好** |
| 例：产品与研发 | 内部专名表 | 场景默认「文档」 |

**为什么默认「通用」而不是强制选择**：不加词表时通用口述的字准确率已有 91.6%，词表只对术语密集的口述有显著帮助。对不需要的用户，加载一份不匹配的词表是**减分**（§5.3 有实测证据）。默认安全 + 可跳过，比强制选择稳妥。

### 4.1 主流程（听写）

```
idle ──快捷键──▶ warming ──task-started──▶ listening ──快捷键/超时──▶ draining
                                                                        │
                    ◀──────────────── 复制/润色 ───────── reviewing ◀────┘
                                                              │
                                                           关闭/超时
                                                              ▼
                                                            idle
```

| 状态 | 界面 | 说明 |
|---|---|---|
| `idle` | 悬浮条隐藏（或缩为状态图标） | 常驻托盘 |
| `warming` | 悬浮条已出现，显示"准备中" | 建 ASR 会话（约 300ms）。**音频从第一帧就开始采集并在本地缓冲**，见下 |
| `listening` | 灰字实时跟随，定稿转白字 | 正常听写 |
| `draining` | 灰字定稿中 | 已停止收音，等服务端收尾（`finish-task` → `task-finished`） |
| `reviewing` | 显示「复制」「润色」「识别错了」 | 结果可操作，同时已写入本地历史 |

**关于 `warming` 的两个设计决定**：

1. **不做会话预热**。百炼按 `usage.duration` 计费，**静音也计费**。若常驻一个空会话或提前建会话，空闲时间全部要付钱。因此会话在按下快捷键时才建立。
2. **音频不丢**。建会话需要约 300ms，这期间**照常采集并在本地缓冲**，`task-started` 到达后立刻把缓冲的音频 flush 出去。这样既不浪费钱，又不会吞掉用户开口的第一个字，也不会额外增加首字延迟。

### 4.2 触发模式

- **按一下开始（toggle）**——默认。口述长文时按住不放很累。
- **按住说话（hold）**——可在设置中切换。适合短句快速输入。

默认快捷键：macOS `⌥Space`，Windows `Ctrl+Shift+Space`。**必须可配置**，且设置界面需要检测与系统快捷键的冲突（Windows 上 `Alt+Space` 是系统菜单、`Win+Space` 是输入法切换，都不能用）。

### 4.3 停止后

- 进入 `draining`，最长等待 20 秒收尾，超时则强制回收并保留已识别内容
- 结果自动写入本地历史（无论用户是否复制）
- 「复制」→ 写入剪贴板 → 悬浮条淡出
- 「润色」→ 展开主应用，内容带入编辑器
- 「识别错了」→ 见 §5.10

### 4.4 润色流程

点「润色」后悬浮条展开为主应用，编辑器内已是口述原文。

1. 选**场景**：邮件 / 即时通讯 / 文档 / 社媒
2. 选**语气**：正式 / 口语 / 简洁 / 热情
3. 点「润色」→ LLM **流式**输出
4. **并排显示**：左原文、右润色结果，用户点「采用」才替换

**并排而非原地替换**是刻意的：口述内容一旦被覆盖就找不回来，而润色结果 LLM 可能改变原意。并排 + 显式「采用」让每一步都可撤销。原文始终保留在历史记录里。

场景与语气预设**可新建、可编辑**，存本地。

## 5. 关键技术设计

### 5.1 技术栈

**Electron + React + TypeScript**。

选型依据是查证过的同类产品而非偏好：拆开 Transync AI 的 Windows 安装包（90.9MB），根目录有 `LICENSE.electron.txt`、`resources/app.asar`、`resources/app-update.yml`，其 Electron 身份确凿。它证明**同品类、同形态（右下角悬浮窗 + 实时字幕）的商业产品可以用 Electron 做出来并上架**。

补充事实，供后续决策参考：

- Transync 的桌面端带一个 `resources/win-native-helpers/transync-win-process-loopback-helper.exe`，用 Windows Process Loopback API 按进程抓会议软件的声音。**即 Electron 并不是全能，系统级能力仍然要靠原生小工具补**——这个分层模式值得照抄。
- 它的 Android 端是**原生 Kotlin**（APK 内有 `classes.dex` + `DebugProbesKt.bin` + `kotlin/`，无 `libflutter.so`、无 React Native bundle）。所以它是**三套独立代码库**，靠版本号对齐，不是一套跨端框架。

**UI 层用 React + TypeScript 编写，与框架解耦**。若将来要迁移到 Tauri，这部分代码可以原样复用——这个决定不是单向门。

### 5.2 音频采集（v1 唯一不可妥协项）

**必须先说清现状问题。** 现有浏览器 demo 的采集链路是：

```js
ctx = new AudioContext({ sampleRate: 16000 });          // demo/public/index.html:459
const ratio = Math.max(1, Math.round(ctx.sampleRate / 16000));
```

`ratio` 只在采样率是 16000 的**整数倍**时才正确：

| 浏览器实际采样率 | ratio | 实际输出 | 结果 |
|---|---|---|---|
| 16000 | 1 | 16000 Hz | 正确 |
| 48000 | 3 | 16000 Hz | 正确 |
| **44100** | **3** | **14700 Hz** | 慢 8.1% |
| **24000** | **2** | **12000 Hz** | 慢 33% |

而服务端硬编码 `sample_rate: 16000`（`spike/lib/asr.js:283`），不会校验。**44100 正是 macOS CoreAudio 最常见的速率**（蓝牙设备尤其如此），Windows/WASAPI 几乎只给 48000 或 16000。

2026-09-05 领导在 **MacBook + Chrome** 上体验 demo，反馈「特别慢，只能识别到几秒前说的话」，而用户在 **Windows + Edge** 上正常。高度疑似与此相关，**但尚未取证**——也可能存在 macOS 上 Web Audio 图时钟与采集时钟漂移（那会造成持续增长且无爆音的滞后，与描述吻合）。

**v1 采集层必须满足以下全部要求**：

1. 用设备**原生**采样率建 `AudioContext`，**不指定** `sampleRate`
2. worklet 内用**小数比线性插值**重采样到 16000，**不用整数抽取**
3. 运行时**断言**实际输出字节率 = 32000 B/s，偏差 >2% 立即在界面报警
4. 发送侧按 **100ms 合批**（3200 字节，百炼官方对新模型的示例值），而不是每 8ms 一包。上行从 125~375 包/秒降到 10 包/秒
5. 加**背压**：`ws.bufferedAmount` 超阈值就丢弃最旧的音频。宁可掉几个字，也不要「越说越滞后」——音频是按 1× 实时推的，一旦落后就永远追不回来
6. **真机 spike 前置**：在 Windows 与 macOS 真机上各验证一次实际采样率、输出字节率、图时钟是否漂移、端到端延迟。**若 macOS 确实漂移，改走原生采集 helper**（参照 Transync 的 `win-native-helpers` 模式），不要勉强用 Web Audio

第 6 条是**里程碑 M1 的准入条件**，不通过不进入 M2。

### 5.3 ASR 与领域词表

| 项 | 取值 | 依据 |
|---|---|---|
| 模型 | `qwen-audio-3.0-asr-flash-streaming` | 官方已把 Paraformer 标为「较早一代，建议迁移」 |
| 链路 | 直连百炼，不走 SmartRouter | spike 阶段避免网关污染延迟数据；转发能力待 v1.1 评估 |
| `max_sentence_silence` | **保持默认 1300**，不改 | 实测改 400 只快 5%，却 3/3 出现末尾幻觉。幻觉是致命缺陷 |
| `semantic_punctuation_enabled` | `false` | VAD 断句，延迟优先 |

#### 领域词表的三条硬约束

**领域词表不是通用增益，是强领域绑定的资产。** 以下三条来自 2026-09-04 实测，不是推测：

| 配置（同一批音频、同一领域） | CER |
|---|---|
| 措辞 A：缩写全大写 + 品牌名首字母大写 | **0.0105** |
| 措辞 B：统一要求全大写 | 0.1965 |
| 加热词 | 0.2081，**并凭空多出一句没说过的话** |

**同一领域只改措辞，CER 差 18 倍，还诱发幻觉。** 由此：

**约束一：每份词表发布前必须实测。** 复刻跨境电商那份的方法——代表性音频 + ground truth + A/B 对照。未测量的词表是**负资产**，不是中性资产。

**约束二：400 字符是硬上限。** `input.context` 最多 5 条消息、总长 ≤400 字符，现有跨境词表已占 162。每份词表只能放「格式指令 + 一小撮高价值术语」，不能堆词，必须按字符预算设计。

**约束三：用户自定义走结构化输入，不开放自由 prompt 文本。** 让用户填「术语列表」+「输出格式（全大写／首字母大写／保持小写）」，系统按已验证的模板拼装。理由就是上表——用户随手写的一句，大概率比模板差，而且是负收益。

#### 本期词表清单

| 词表 | 状态 | 说明 |
|---|---|---|
| 通用（无词表） | **默认** | 不加词表时通用口述字准确率已 91.6% |
| 公司内部专名表 | **v1 新建** | 产品名、内部系统名、项目代号、常用缩写、高频同事姓名。素材从内部文档与产品清单拉取 |
| 跨境电商词表 | **本期不启用** | 已完成实测（术语命中 5/9 → 9/9），但内部同事 ≠ 跨境卖家（§2.1）。留待对外试用时启用 |

#### 内部专名表的产出路径（依赖 F10）

不要凭空列词表，按数据走：

1. 内部试用先跑**通用词表**（无词表）
2. 用 F10 的「识别错了」标记收集错误样本
3. 统计高频错误词 → 得出候选术语表
4. 按字符预算拼装成 prompt，**A/B 实测验证**
5. 通过后由 F11 集中下发

这样词表是从真实错误里长出来的，而不是我们猜的。

### 5.4 润色（LLM）

- 走 **SmartRouter**（自有 OpenAI 兼容网关）——**需先验证其流式能力**
- 流式输出，逐字上屏
- 场景：邮件 / 即时通讯 / 文档 / 社媒
- 语气：正式 / 口语 / 简洁 / 热情
- 预设可新建、可编辑，存本地
- 并排显示，显式「采用」才替换
- **场景默认值由首次使用选择的职业驱动**（§4.0）

### 5.5 本地历史

- 本地 SQLite
- 字段：时间、原文、润色后文本、场景、语气、音频时长
- 全文搜索：SQLite FTS5。**中文需要分词方案**（FTS5 默认分词器对中文无效，需用 trigram 或 bigram 分词器）
- **不上传**

### 5.6 悬浮条不抢焦点（平台差异最大处）

| | Windows | macOS |
|---|---|---|
| 不激活 | `WS_EX_NOACTIVATE` + `WS_EX_TOOLWINDOW` | `NSPanel` + `NSNonactivatingPanelMask` |
| 置顶 | `SetWindowPos(HWND_TOPMOST)` | `NSScreenSaverWindowLevel` 或 `NSStatusWindowLevel` |
| 注意 | 禁止调用 `SetForegroundWindow` | 需要辅助功能权限才能全局生效 |

两个平台都需要 `setIgnoreMouseEvents(true)` 让鼠标点击穿透，鼠标移入悬浮条时临时关闭穿透（否则按钮点不到）。

### 5.7 权限、签名与内部分发

| 项 | Windows | macOS |
|---|---|---|
| 麦克风权限 | 系统弹窗 | `NSMicrophoneUsageDescription` |
| 全局快捷键 | 无额外权限 | **需要辅助功能权限**（系统设置 → 隐私与安全性） |
| 签名 | 内部分发可不签名（SmartScreen 警告，点「仍要运行」） | **建议仍走 Developer ID + 公证**（$99/年） |
| 分发 | 内部下载页 | 内部下载页（dmg / pkg） |

**macOS 为什么还建议公证**：不公证的话，每位同事第一次都要「右键 → 打开」绕过 Gatekeeper，更新后可能还要再来一遍。50 人规模下这个摩擦很劝退，$99/年换来免打扰是划算的。

**权限引导（F12）是给非技术同事做的，不能省。** macOS 辅助功能权限要手动去「系统设置 → 隐私与安全性 → 辅助功能」里勾选，非技术同事第一次大概率找不到。必须做分步图文引导，并在设置页实时显示当前授权状态。这一项不做，会吃掉大量一对一支持时间。

签名与公证只能在 macOS 上完成（`codesign` 属 Xcode 命令行工具）。已确认可申请/借到一台 Mac。

### 5.8 API Key 的分发与保管

**`app.asar` 是可以被解包的，里面的字符串等于明文。** 因此 **Key 不内置在安装包里，改由 F11 配置端点下发**（端点要求见 §5.9）。

#### 先说清楚一件事：这不是更安全，是换了地方放钥匙

| | 内置在包里 | 经配置端点下发 |
|---|---|---|
| 谁能拿到 | 任何拿到安装包的人，离线解包即可 | 任何能访问配置端点的人 |
| 随包外泄 | **会**，包外泄 = Key 外泄 | 不会 |
| 轮换成本 | 重新打包 + 全员更新 | 改服务端，下次启动自动生效 |

安全级别由此从「应用包有多难解」变成「配置服务器有多难进」。内部试用阶段两者实际暴露面相近，所以**下发的价值主要在运维而非保密**：

1. **轮换与吊销不用发版**——Key 到期或泄露时改服务端配置即可，50 台机器自动生效
2. **不随包外泄**——内部工具的安装包很容易被随手转发出去
3. **可按人下发不同 Key**——顺带得到成本归属能力（哪个部门烧了多少钱）

#### 客户端侧的保管要求

- Key 只在**主进程**持有，通过 `contextBridge` 暴露最小接口，渲染进程永不接触明文
- 落盘使用 Electron `safeStorage`（Windows DPAPI / macOS Keychain）
- 配置端点返回的 Key 带版本号，客户端发现版本变化即更新本地缓存
- **未取到 Key 时的行为要明确**：提示「未获取到授权，请联系管理员」，而不是静默失败或降级到某个内置默认值

#### 真正的答案是服务端代理，但本期不做

根治方案是客户端根本不持有 Key：客户端连内部服务器，服务器注入 Key 再转发百炼，Key 永不离开服务器，还能集中做配额与审计。

**本期不做的理由**：它是单点故障、多一跳延迟、多一套要运维的服务，而当前目标是收集反馈不是防攻击。等对外发布时，这件事本来就要跟着 SmartRouter 一起做（网关正是这个角色）——那时做是顺带的，现在做是额外的。**在此之前接受「客户端持 Key」这个风险。**

### 5.9 分发、更新与配置下发（F9、F11）

50 人以上规模，手动发安装包不可行。**更新端点与配置端点必须分开**——两者的机密性要求完全不同，共用一个 HTTP 目录等于把 Key 的防护降级到「能访问文件服务器即可」。

#### 自动更新（F9）

- `electron-updater`，更新源指向内部静态服务器
- 更新包本身不含密钥，HTTP/HTTPS 均可，但**必须校验更新包签名**。否则内网中间人可以替换更新内容推一个恶意版本给 50 台机器——这是比 Key 泄露严重得多的问题
- macOS 上更新的签名与公证要求同 §5.7

#### 配置端点（F11）

一个版本化 JSON 配置，应用启动时拉取。**因为要承载 API Key（§5.8），要求比更新端点严格**：

| 要求 | 说明 |
|---|---|
| **HTTPS** | 不能是裸 HTTP。内网不等于可信网络 |
| **访问控制** | 端点不能是公开 URL，否则任何人 `curl` 一下就有 Key。至少要有设备凭据或内网边界限制 |
| **访问日志与限流** | Key 分发是被攻击的目标，要有审计能力 |
| 版本化 + 灰度 | 支持先给部分人下发新配置（如新词表） |

配置内容：预置词表列表与内容、默认快捷键、默认场景/语气、**API Key 及其版本**。

容错要求（与 Key 无关但同样关键）：

- 本地缓存上次成功的配置；拉取失败时**静默使用缓存，绝不阻塞启动**
- 配置 schema 要做校验，服务端返回了损坏配置时回退到缓存，不能让 50 台机器同时启动不了
- 未取到过任何配置（如首次安装且服务器不可达）时，走到 §5.8 的明确提示路径

### 5.10 遥测、反馈与隐私（F10）

这是内部试用的全部意义所在，必须做成功能，不能靠口头收集。

**自动上报**（本地聚合，每小时一次摘要；异常实时上报）：
- 崩溃与异常堆栈
- 每次听写：时长、字数、首字延迟、定稿延迟、失败原因、平台与系统版本

**用户主动反馈**：悬浮条 `reviewing` 状态提供「识别错了」按钮。
- 点击后标记该次听写
- 用户可补充「正确应该是什么」
- **音频片段需逐次确认才上传**，默认不上传（见下方隐私）

为此需要**本地临时缓存最近约 10 分钟的音频**（内存或临时目录，退出即清，不落持久存储），否则用户事后标记时音频已经没有了对证。

**隐私规则（内部试用同样要守）**：
- 默认**只上报文本指标**，不上传音频
- 上传音频片段必须**逐次确认**，不是一次性同意
- 设置里可整体关闭遥测
- 上传内容仅用于改进识别，不做其他用途，需在引导页写明

顺带说明：这套机制同时是**补齐 ground truth 的最短路径**（§9 R3）。内部几十人日常标记，攒出来的就是真实场景的错误样本，比人工听录音核对快得多，而且覆盖真实口述而非照稿念。

## 9. 风险与开放问题

**R1 macOS 采集风险（最高）** — 2026-09-05 领导在 MacBook 上体验明显劣于 Windows，原因未取证。若 M1 证明 Web Audio 在 macOS 上不可用，需改原生采集 helper，M2 排期要重估。**这台机器就是决策者的机器，出问题代价最大。**

**R2 会议记录有硬边界，必须先对齐场景** — 百炼**所有实时模型都不支持说话人分离**，只有离线模型支持。分两种：
- 一对一线上会议（我 + 对方）→ 麦克风 + 系统音频两路独立 ASR 会话，**能做**，代价双倍 ASR 费用。Transync 正是这么做的（用 Process Loopback API 抓会议软件声音）。
- 同一麦克风前多人（会议室圆桌）→ 需要真声纹分离，**实时无解**，等于另一个产品。

**注意 macOS 没有按进程抓音频的 API**：Windows 有 Process Loopback，macOS 只能装虚拟声卡（BlackHole 等）或用 ScreenCaptureKit（macOS 13+，只能全屏采集、不能按进程）。所以将来做会议，macOS 这块无论如何都是硬骨头，**与选什么框架无关**。本期只锁定个人听写，会议记录仅保留扩展位。

**R3 准确率无数据 —— 已找到解，但依赖 M5/M6** — 字准确率与「draft→corrected 修正增益」两项至今缺 ground truth（`01-dictation.draft.txt` 未经核对，故意未用正式文件名）。内部试用 + F10 错误标记是补齐它最快的路径。若 M5 被推迟，A5 将无法验收。

**R4 SmartRouter 流式能力未验证** — 润色功能依赖它做流式输出。若不支持流式，M4 的用户体验会明显下降（要等整段生成完）。需在 M4 之前单独验证。

**R5 中英夹杂仍是短板** — 换模型后字准确率 83.2% → 91.6%，加上下文增强后术语命中 9/9。但**该词表是跨境电商专属，对内部同事无用**（§2.1）。内部专名表的效果未知，必须实测后才能下发。

**R6 一人开发 + 双平台 + 50 人支持** — 涉及 Electron、React、SQLite、两个操作系统的窗口管理、签名公证、两条 CI、内部分发与更新、遥测后端。50 人规模还会带来持续的支持负担（快捷键冲突、权限、不同机器性能）。**建议 M2/M3 或 M4/M5 找人并行**，否则周期会很长；同时 F13 诊断导出必须做，否则远程排查 50 台机器会是噩梦。

**R7 端到端语音大模型的竞争** — Transync 用的是端到端语音模型。我们是 ASR + LLM 两段式。两段式的优势是可控、可替换、可按场景定制；劣势是链路更长。需持续关注。

**R8 百炼 RPM 限流可能直接卡死 50 人试用（未核实，优先级高）** — qwen-audio-3.0 的限流为 **1200 RPM**，**但计数口径未知**。若 duplex 流里的音频二进制帧也计入请求，按我们 100ms 合批的节奏：

```
10 帧/秒 × 60 = 600 次/分钟/人
50 人        = 30,000 次/分钟   →   远超 1200
```

**即使只有 2 人同时说话也会撞上限。** 若按 `run-task` 计，则 50 人绰绰有余。

这个数字能直接决定 50 人试用是否可行，且**与 Key 怎么分发无关**——只要共用 Key 就存在。必须在 **M1 阶段**查清官方口径或直接压测。

若确实按帧计，两条出路：
- **每用户独立 Key**——§5.8 的下发方案正好支持，且顺带得到成本归属能力
- **服务端代理做集中排队与配额**——即 §5.8 提到但本期不做的方案，届时需要提前到 M5

**开放问题**：
- 产品名与商标查询未做（VoicePilot / 闻字 / 出口成章）
- 内部专名表的具体词条来源与责任人未定（需从内部文档拉取）
- 遥测后端用自建还是现成服务（Sentry / 自建）未定
- 悬浮条是否常驻显示，还是只在听写时出现——取决于实测抗干扰程度，M2 中定
- 内部试用是否要强制开启遥测（建议：默认开启、可关闭，但明确告知关闭后无法改进）
